## 1. 目标识别

「畅课」是 **TronClass**（WisdomGarden 出品的 LMS）的中文名。各校使用**独立租户域名**，接口路径与语义一致：

| 学校（示例） | 网页版域名（示例） |
| --- | --- |
| 学校 A | `https://courses.school-a.edu.cn` |
| 学校 B | `https://lnt.school-b.edu.cn` |
| 学校 C | `https://courses.school-c.edu.cn` |

因此脚本不需要预先知道具体学校：绑定任意租户域名后，接口路径通用。

## 2. 接口口径（实测来源见文末）

### 2.1 身份与会话

```
GET  /api/profile                       -> { id: <student_id>, ... }
GET  /api/current-semester-info         -> { semester.id, academic_year.id }
POST /api/my-courses                    -> 课程列表（需 conditions.semester_id / academic_year_id）
```

- 网页版**无需自建登录**：浏览器里已登录的 cookie 即会话，脚本同源调用即可。
- 部分版本额外要求请求头 **`x-session-id`**（会话标识，随页面自身请求下发）。脚本通过 hook `XMLHttpRequest.setRequestHeader` 与 `window.fetch` 抓取该值复用。
- 旧版 App 走 OAuth：`POST /api/login?login=access_token` body `{access_token, org_id}`，响应头返回 `x-session-id`。网页版用不到。

### 2.2 两种 status，别搞混（关键坑）

| 来源 | 字段 | 含义 |
| --- | --- | --- |
| `GET /api/course/{cid}/student/{sid}/rollcalls` | `status` | **本人**状态：`absent` = 未签，`on_call_fine` = 已签 |
| `GET /api/rollcall/{rid}/student_rollcalls` | 顶层 `status` | **点名本身**状态：`in_progress` / `finished` |

课程列表接口的 `end_time` 恒为 `None`；结束时间只能从点名详情取。
拿详情顶层 status 判「本人签没签」会把已签的误报成失败。

### 2.3 签到提交（均为 `PUT`，JSON body）

```
PUT /api/rollcall/{rid}/answer_number_rollcall   { deviceId, numberCode }        # 数字签到
PUT /api/rollcall/{rid}/answer_qr_rollcall       { data, deviceId }              # 二维码签到
PUT /api/rollcall/{rid}/answer                   { latitude, longitude,
                                                   accuracy:35, altitude:0,
                                                   altitudeAccuracy:null, heading:null,
                                                   speed:null, deviceId }          # GPS/雷达签到
```

- `deviceId` 每次为新生成的 UUID v4。
- 成功判据：HTTP 200；稳妥做法是回查名单确认本人 `rollcall_status == on_call_fine`。

### 2.4 数字码的取码通道（**2026-10-10 服务端改动**）

```
老通道  GET /api/rollcall/{rid}/student_rollcalls  -> number_code
        自 2026-10-10 起该字段恒为 null

新通道  GET /api/timetable_rollcalls?course_ids={cid}&rollcall_date={YYYY-MM-DD}
        返回 { rollcalls: [ { id, number_code, ... } ] }
        · rollcall_date 取点名时间 rollcall_time 的 **UTC 日期**
        · 点名结束后 number_code 仍保留
        · 参数须为单值/重复参数，传数组形式会返回空
```

### 2.5 已签人数（门控用）

`GET /api/rollcall/{rid}/student_rollcalls` → 名单数组 `student_rollcalls[]`，
统计 `rollcall_status == "on_call_fine"` 的人数即已签人数，数组长度即应到人数。

⚠️ 不能用 `updated_at` 判已签：缺勤学生从建记录起就带该字段。

## 3. 二维码签到：自定义压缩编码（真·逆向成果）

二维码内容是一段 `!key~value!key~value` 的紧凑编码：

- 分段符 `!`（0x21），键值符 `~`（0x7E）
- **key** 是字段序号的 **base36**，字段顺序固定：

  | 序号(b36) | 字段 | 序号(b36) | 字段 |
  | --- | --- | --- | --- |
  | 0 | courseId | 6 | accessCode |
  | 1 | activityId | 7 | action |
  | 2 | activityType | 8 | enableGroupRollcall |
  | 3 | data | 9 | createUser |
  | 4 | rollcallId | a | joinCourse |
  | 5 | groupSetId | | |

- **value** 前缀为控制字符时的含义：
  - `chr(26)` + `1` / `0` → 布尔 true / false
  - `chr(26)` + 其他 → 枚举值（`chr(26)+2`=classroom-exam，`+3`=feedback，`+4`=vote）
  - `chr(16)` + base36 数值；多点分隔（如 `x.y`）拼成浮点数
  - 无前缀 → 普通字符串，其中 `chr(31)` 还原为 `~`、`chr(30)` 还原为 `!`

- 二维码常以 URL 形式出现：`/j?p=...` 或 `/scanner-jumper?...`；
  `_p` 参数为直接 JSON，`p` 参数为上述压缩串。解析后取 `rollcallId` + `data` 即提交所需字段。

**但：二维码内容无法自行获取。** 其 token 是服务端密钥哈希，学生端没有下发接口
（老师投屏的码只存在于屏幕上）。所以二维码签到**只能**在拿到码内容（拍照/能看到码）后提交。

## 4. 各类签到的自动化可行性（2026-10 现状）

| 类型 | 能否全自动 | 说明 |
| --- | --- | --- |
| 数字签到 | ✅ 可以 | 轮询发现 → 取码（新通道）→ PUT 提交，闭环 |
| 普通/点击签到 | ⚠️ 推断 | 接口为 `PUT /api/rollcall/{rid}/answer_rollcall`（**无实测证据，属类比推断**），脚本默认关闭，需手动开启 |
| 二维码签到 | ⚠️ 取决于一个授权点 | 服务端确有取码接口 `GET /api/course/{cid}/rollcall/{rid}/qr_code`。学生会话若能读 → **可全自动、无需拍照**（脚本已实现自动取码 + 亚秒级轮询）；读不到则退回粘贴码内容。详见 §9 |
| GPS / 雷达签到 | ⚠️ 半自动 | `PUT answer` 需精确坐标；**三角定位法已于 2026-10-12 失效**（越界提交不再返回距离），只能手填教室坐标 |
| 教师端发布签到 | — | 服务端推送，学生端靠轮询/页面刷新感知，无公开推送订阅接口 |

## 5. 其他工程细节

- 畅课网页版是 **hash 路由 SPA**（`#/<activityId>`），整站不刷新，因此轮询优于 DOM 监听。
- 页面全局变量暴露 `globalData.course` / `st` 等，可用于定位当前课程。
- 建议的**签到门控**策略（避免总是第一个签、降低被注意的概率）：
  已签人数 > 全班 1/4 **或** > 20 人再签；
  保底放行：拿不到名单 / 等待超 120s / 距结束不足 30s（漏签比早签更糟）。

## 9. 二维码 token 机制与「免拍照」路径（2026-10-19 补证）

### 9.1 token 的结构与生命周期

来自 `hot-YUser/auto-Tronclass-VPS`（`qr_common.py`）的严格校验实现：

```python
TOKEN_RE = re.compile(r"[0-9]{10}[0-9a-f]{32}\Z")   # 10 位十进制 + 32 位十六进制
embedded = int(data[:10]);  embedded != ts → "timestamp_mismatch"
age_ms = now_ms - ts * 1000
age_ms > stale_ms   → "stale"      # QR_STALE_MS=3000
age_ms < -future_skew_ms → "future" # QR_FUTURE_SKEW_MS=1000
```

即：**`data` = 10 位 Unix 秒 + 32 位 hex 签名**，且**生命周期只有数秒**（该项目按 3 秒判过期、以 0.5 秒轮询续采）。
32 位 hex = 128 bit，形态上与「服务端密钥对时间戳（可能附带点名上下文）的签名」一致。

### 9.2 token 的来源接口

```
GET /api/course/{course_id}/rollcall/{rollcall_id}/qr_code   ->  { "data": "<token>" }
```

提交仍是 `PUT /api/rollcall/{rid}/answer_qr_rollcall  { data, deviceId }`。

### 9.3 已知唯一可用实现的取码方式（关键证据）

`auto-Tronclass-VPS` 的 keeper 流程（`qr_keeper.py`）：

1. 以 **教师账号**登录（`QR_TEACHER_USER/PASS`，`QR_BASE=https://www.tronclass.example`）
2. **自己创建并启动一个 QR 点名**：`POST /api/course/{cid}/rollcall`（`type: qr_rollcall`）→ `POST /api/rollcall/{rid}/start-rollcall`
3. 以 `QR_POLL_SECONDS=0.5` 高频轮询 `GET /api/course/{cid}/rollcall/{rid}/qr_code`，取出 `body["data"]`
4. 通过自己的只读 HTTP API 转发给客户端（`qr_keys.py` 管的是**它自己 API 的访问密钥**，与 TronClass 服务端密钥无关）
5. 另有 `QR_CORPUS_*`：可选把原始 token 落盘成语料（默认关闭，上限 16 GB / 30 天）——应是作者长期采集以研究生成规律

**这反证了两点**：token 不能由学生端已有信息推导（否则无需教师账号高频采集）；token 随点名滚动重发，单次拍照所得仅在数秒窗口内可用。

### 9.4 免拍照的三条路径

| 路径 | 前提条件 | 现状 |
| --- | --- | --- |
| **学生会话直读取码接口** | 该接口未做教师角色/归属校验 | **待测**：脚本面板「探测取码权限」一键给出结论（单次 GET） |
| 服务端不校验 token 内容 | 提交任意 `data` 也返回 200 | 可用粘贴框发一条无效 data 试探 |
| 教师会话采集 | 需要教师账号凭据 | 技术可行，但属未授权访问他人账号 —— 不做 |

### 9.5 实测步骤（各一次请求，有界、非破坏性）

1. 老师发起二维码签到后，在面板点 **「探测取码权限」**，看是否 `HTTP 200` 且返回 token；
2. 若 200：勾选 **「自动取码」**，脚本以 0.7s 轮询 `qr_code`，token 未过期即立即提交 → **全程不需要拍照**；
3. 若 403/404：学生会话无权读取，退回人工路径（拍照或同学转发码内容 → 粘贴框提交）。

> 补充来源：`hot-YUser/auto-Tronclass-VPS`（2026-08-19 创建，2026-10-02 更新）——「TronClass 公有雲 QR 點名 data 服務」。

## 10. 客户端静态取证（2026-10-19，本机真机包）

取证对象：`/Applications/TronClass.app`，结构 `TronClass.app/Wrapper/TronClass.app/`（"Designed for iPad" 的 iOS-on-Mac 包）。
客户端形态：**Capacitor/Cordova 混合应用**（`capacitor.config.json`、`config.xml`、`CDVCapture.bundle`）；
主二进制仅 137 KB（arm64，纯壳），**全部业务逻辑在前端 bundle**：`Wrapper/TronClass.app/public/js/`，14 MB / 293 个 chunk。
→ 等于直接在本地拿到了网页版前端的压缩源码，可静态审读。

### 10.1 二维码解码器：与本书 §3 移植实现逐行比对

真实客户端实现（`chunk-vendors-48b8d778.08962c97.js`）：

```js
Qi=String.fromCharCode(30), Ji=String.fromCharCode(31), eo=String.fromCharCode(26), to=String.fromCharCode(16),
no=eo+"1", ro=eo+"0",
uo=Object.fromEntries(["courseId","activityId","activityType","data","rollcallId","groupSetId","accessCode",
    "action","enableGroupRollcall","createUser","joinCourse"].map((e,t)=>[e,t.toString(36)])),
io=Object.fromEntries(["classroom-exam","feedback","vote"].map((e,t)=>[e,eo+Number(t+2).toString(36)])),
oo=反向映射(uo), ao=反向映射(io),
lo=e=>{ ... e.split("!").filter(Boolean).forEach(part=>{ const n=part.split("~"); ...
      key = oo[n[0]] || n[0];
      value = u.startsWith(eo) ? (u===no || (u!==ro && (ao[u]||u)))
            : u.startsWith(to) ? (t=u.substring(1).split(".").map(x=>parseInt(x,36)), t.length>1 ? parseFloat(t[0]+"."+t[1]) : t[0])
            : u.replaceAll(Ji,"~").replaceAll(Qi,"!") }) }
```

**结论：字段顺序（11 项）、四个控制字符、key 的 base36 映射、枚举/布尔/整数/浮点的判定分支，全部与本书移植实现一致。**

唯一差异（良性）：客户端用 `part.split("~")` 取 `n[1]`，即遇到第二个 `~` 会截断其后内容；移植实现取首个 `~` 之后的全部。因合法载荷把 `~` 转义为 `chr(31)`，两者对真实数据**等价**。

### 10.2 token 是服务端生成并服务端校验——三条硬证据

1. **服务端校验错误码表**（`app.aa084c54.js`）：
   ```
   QR_ROLLCALL_NO_REQUEST_DATA        = "no_request_data"
   QR_ROLLCALL_INVALID_QR_CREATE_TIME = "invalid_qr_create_time"
   QR_ROLLCALL_INVALID_CREATE_TIME_HASH = "invalid_create_time_hash"   ← 关键
   QR_ROLLCALL_CODE_EXPIRED           = "qr_code_expired"
   QR_ROLLCALL_UNKNOWN_STUDENT        = "rollcall_unknown_student"
   QR_ROLLCALL_NOT_FOUND              = "not_found_qr_rollcall"
   ```
   → 载荷内含 **create_time**，服务端还要校验一个 **create_time 的 hash**，并强制时效（expired）。
   这正是 §9.1 里 `[0-9]{10}[0-9a-f]{32}` = `create_time + create_time_hash` 的语义来源。

2. **编码器不在客户端**：整个 bundle 中**不存在**紧凑编码器（无 `.join("!")`）。
   解码在客户端、编码不在 → 载荷（含 create_time 与 hash）由服务端生成。**客户端拿不到 secret，无法自造 token。**

3. **教师端只做新鲜度校验**（`366.8ea4e702.js`，教师点名页）：
   ```js
   X = e => { if(!e) return;
              const l = moment(e).utc().diff(moment().utc(),"seconds");
              Math.abs(G.value - l) > 3 && ( ... ) }
   ```
   对收到的 create_time 做 **±3 秒**判定 —— 与采集项目的 `QR_STALE_MS=3000` 一致；且该页通过实时通道
   `(0,y.s)("/rollcall", {rollcall_id})` 接收 `answer_qr_rollcall_success` / `rollcall_stop` 事件，
   说明 token 是由服务端**滚动下发**的，不是本地算的。

### 10.3 客户端 rollcall 接口全表（权威）

```

getRollcalls            /api/course/{cid}/rollcalls
```

**两处纠正/确认：**

- **不存在 `answer_rollcall`**。此前按类比推断的普通签到端点属**错误结论**；普通/其他类型实际走
  `PUT /api/rollcall/{rid}/answer?api_version=1.76`（与 GPS/雷达同一端点）。脚本已修正。
- **客户端全表里没有 `qr_code`** → 采集项目使用的 `GET /api/course/{cid}/rollcall/{rid}/qr_code`
  是**未被 shipped 客户端引用的未公开端点**（服务端存在，但学生端是否放行未知，必须实测）。
- 另注：本项目客户端（2026-10-09 构建）**不含 `timetable_rollcalls`**；该接口是 XMU 侧网页版实测到的取数字通道，
  说明不同客户端/版本在取码方式上存在差异。

### 10.4 免拍照的最终判定

**不能"算"，只能"取"。** token 由服务端用密钥生成（create_time + create_time_hash），
客户端无编码器、无 secret，且仅数秒有效；128 bit 的 hash 也无法暴力枚举。

因此唯一现实路径仍是 §9.4 的三条；脚本的「探测取码权限」已把候选端点扩为 4 条（有界，每条一次 GET）：

```
/api/course/{cid}/rollcall/{rid}/qr_code        ← 采集项目实测有效，学生会话权限未知
/api/rollcall/{rid}/lite
/api/rollcall/{rid}/answers
/api/courses/rollcall_status/{rid}/result
```

命中判定：响应中出现符合 `^[0-9]{10}[0-9a-f]{32}$` 的字段即视为取到 token，随后脚本会立即
`answer_qr_rollcall` 提交（token 未过期时）。

## 11. 二维码：载荷形态补齐 + 决定性实验（2026-10-19 晚）

### 11.1 载荷可能不是紧凑编码，而是 JSON（客户端静态取证）

该客户端 `scanner-jumper` 的进入逻辑是：

```js
if (e.includes("_wg_p=")) o = e.split("_wg_p=")[1];
else if (e.includes("/j?p=")) o = e.split("/j?p=")[1];
if (!o) return error("Error: miss params！");
let l = JSON.parse(o)        // ← 这一版的载荷就是 JSON
```

判定是否进入课堂活动靠字符串里有没有 `"activityType":` / `/j?p=` / `/_wg_qr?_wg_p=`。
⇒ **载荷存在三种形态**：JSON、紧凑串（`!k~v!`，见 §3）、以及它们的 URL/深链包装。
解析器已全部支持（脚本里 `resolveQrPayload` / 守护进程里 `parse_qr_payload`）。

### 11.2 「不扫码直接提交」的障碍在哪

客户端**本身就实现了免扫码提交**：把载荷（含 `data`）喂给它（深链或 `/j?p=` 路由）即直接进入
课堂活动并提交。⇒ **技术障碍不在客户端，而在"载荷从哪来"**。

同时排除一个候选：`getRollcallInfoLite`（`/api/rollcall/{id}/lite`）只在 `bluetoothRollcall`
且 lmsVersion ≥ 1.76.0 时调用，取 `{id, useBeacon}` —— 蓝牙点名用，**不是二维码 token 的下发口**。

### 11.3 决定性实验：服务端到底校不校验 `data`

客户端里带有服务端错误码 `no_request_data` / `invalid_create_time_hash` / `invalid_qr_create_time` /
`qr_code_expired` —— 提示服务端会校验，但**此前从未实测**。已实现为一次有界请求：

```
PUT /api/rollcall/{rid}/answer_qr_rollcall   { data: <10位秒 + 32个'f'> , deviceId }
  · 200                          → 服务端不校验 ⇒ 免扫码提交可行，可全自动化
  · invalid_create_time_hash ... → 确实校验 ⇒ 无算法捷径，只能"取得"真实 token
```

触发方式：
- **守护进程**：二维码点名取码失败（403/404）时**自动**执行一次（每点名最多一次）；
  若判定为"不校验"，此后所有二维码点名直接提交占位 data 自动签到。
- **浏览器面板**：新增「探测服务端校验」按钮，当场给结论。

### 11.4 载荷入口：本地接口

既然障碍是"载荷从哪来"，守护进程提供本地接口，**任何来源的载荷都能立即提交**：

```bash
curl -s http://127.0.0.1:8788/qr -H 'Content-Type: application/json' \
  -d '{"payload":"<任意形态载荷：JSON / 紧凑串 / /j?p= / _wg_p>"}'
# 或直接给字段：
  -d '{"rollcallId":"123456","data":"1792425000aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}'

python3 changke_daemon.py qr-payload '<载荷>'      # 命令行等价用法（也可用管道喂入）
```

仅监听 `127.0.0.1:8788`，可用 `qr_api_token` 加共享令牌。

### 11.5 结论（未变，但边界更清楚了）

token 仍是 `create_time + create_time_hash`，**服务端生成、服务端校验**，客户端无编码器、无密钥，
128 bit 无法枚举 ⇒ **不可"算"**。可做的只有"取"，而现在"取到之后怎么用"这条路已经完整打通：
拿到载荷 → `POST /qr` 或粘贴 → 立即提交。
